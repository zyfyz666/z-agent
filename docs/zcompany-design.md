# ZCompany 设计草案

状态：产品与技术方案，尚未接入应用。2026-10-08。

核心目标：支持真正的长时运转。执行服务独立于界面，工作状态持久保存，成员按需协作，观察者维护全局目标与成果的一致性。详细运行契约见 [长时运行与全局观察者设计](zcompany-runtime-design.md)。

## 1. 产品定位

Z 保留两个并列的工作模式：

- **Agent**：沿用现有单个主 Agent 加临时子代理的工作方式，适合直接解题、编辑项目和执行工具。
- **Company**：围绕共同目标组织一组具有独立身份、会话、模型和工具权限的 ZAgent。成员可以直接讨论、请求协作、提供证据和汇报成果；协作状态独立保存。

Company 的工作对象可以是软件、论文、研究、数据分析或内容制作。“公司”表达持续分工与协作关系，不要求模拟职级，也不要求每次执行之前全员开会。

用户给出目标后，可以持续与负责人对话，也可以直接向成员提问、发引导、调整分工。负责人对整体交付负责，但成员之间不必通过负责人转述。

## 2. 成员与工作项

第一版一个 Company 工作区对应一个项目目标。成员身份可以持续保留；每项具体工作另建工作项。换目标时不会悄悄复用旧任务上下文。

默认从三位成员开始：

| 成员 | 职责 | 默认行为 |
| --- | --- | --- |
| 负责人 | 澄清目标、拆分工作、协调依赖、处理分歧、汇总交付 | 可以亲自完成简单工作，按需调用其他成员 |
| 执行成员 | 研究、实现、分析或制作产物 | 可与其他成员直接交流，工具权限按工作项配置 |
| 验证成员 | 独立核验结果、提出有证据的问题 | 默认只读，提交问题与验收结果 |

用户可以增加、删除、改名和暂停成员，也可以选择不同的团队模板；成员名称不会自动赋予权限。复杂项目可以增加多个并行执行成员。

每位成员分别设置供应商、模型、思考强度、输出上限、上下文压缩阈值、工具权限和观察者开关。共享供应商连接配置，凭据仍留在原配置位置；成员记录只保存引用。修改成员 A 不影响成员 B，正在运行的一轮保留启动时的配置。

每项工作至少包含：目标、负责人、预期产物、验收条件、依赖、可操作范围和预算。任务状态为待安排、就绪、执行中、受阻、待验证、已完成或已取消。提交报告与通过验收分开记录。

## 3. 三种协作方式

### 直接交流

成员可以给另一成员发送问题、发现、变更建议、检查请求或成果。消息关联具体工作项，支持引用文件、差异、日志、来源和附件。

例如，研究成员发现论文中的某个基线分类错误，可以直接把论文出处与修改建议发给正在写作的成员；无需等待负责人重新分配一次任务。

### 小组讨论

成员围绕一个具体问题开启讨论，只邀请相关成员。每次发言应带来新证据、方案、问题或决定。消息不默认广播到所有人的上下文，旁观成员可以从讨论记录按需查看。

存在分歧时，优先设计小实验或检查来源。默认连续两轮没有新证据就停止自动扩展讨论，由工作项负责人记录取舍；该阈值可以配置。涉及用户偏好或超出授权的取舍时才向用户提问。

### 工作汇报

成员在产物完成、依赖受阻、出现重要风险或目标变化时汇报。报告包含完成内容、证据、产物、未解决问题和下一步，而不是只有“已完成”。负责人最终结合验收结果向用户交付。

普通进度与自动收件回执只更新界面，不让所有成员调用模型回复“收到”。

## 4. 消息必须真正推动工作

通信由独立的 Company 调度服务处理，不依赖当前打开哪个对话。

| 接收方状态 | 处理方式 |
| --- | --- |
| 正在运行 | 存入收件箱，在下一次模型请求的安全边界纳入相关消息；不强制取消正在执行的工具 |
| 已结束或空闲 | 需要处理的问题、验证结果或依赖完成通知进入持久待办，并自动启动下一轮 |
| 等待工具 | 普通成员消息先排队；超时和取消由工具运行管理负责，不能靠聊天解决挂起进程 |
| 用户主动暂停或停止 | 保留未读消息与待办，不自动重启该成员或项目 |

消息界面明确区分“已保存”“等待纳入请求”“已纳入请求”“已确认模型响应”“已回应”“问题已解决”。请求出错时保留未确认状态，不能把消息已写入磁盘等同于模型已经收到。

成员消息标明真实发送者和来源，不伪装成人类用户输入。用户最新指令优先，成员之间的请求不能扩大项目目录、工具或外部操作权限。取消、回退与修改目标后，旧版本消息不得继续唤醒新版本任务。

### 调度可靠性

- 同一成员同时只执行一轮；不同成员在项目与应用的并发限制内并行。
- 消息先持久化再安排唤醒，通过消息编号、运行批次、处理回执和带期限的领取记录去重。
- 消息交付允许重试，使用幂等处理避免重复注入与重复执行；不承诺数据库之外的操作能够天然“恰好执行一次”。
- 重启后检查未处理消息、运行租约和已有产物。上次工具是否执行不确定时标为待核实，不能直接重做提交、部署或文件修改。
- 检测任务依赖环、成员互相等待和无新证据的重复讨论；向负责人提出具体阻塞原因。
- 第一版建议默认最多三个并发模型请求，可调整；成员数不等于同时运行数。项目预算同时覆盖讨论、执行、验证和负责人汇总。
- 第一版将独立 Company 执行服务列为必要能力。关闭或重启桌面界面不停止执行；明确的项目暂停、停止操作才改变运行状态。执行主机断电期间无法计算，重新上线后核对并恢复；本机关机后继续运行，需要将服务实际部署到其他在线主机。

## 5. 公司知识与个人上下文

公司共享的是共同目标、需求、术语、已经确认的决策、产物和证据索引。成员保留自己的执行上下文和工作笔记。成员可以通过授权的检索读取相关讨论和报告，但不自动复制所有人的完整历史。

每条共享知识带有来源、适用项目、版本、状态和替代关系。“提议”“待验证”“已确认”分别存储；成员的猜测不能直接成为公司事实。负责人负责确认项目决策，事实类内容需要关联可复查证据。

成员上下文压缩、回退和恢复使用独立会话身份与边界校验。公司讨论也单独存档；成员回退自己的对话，不会删除别人已经收到的消息或修改共享文件。已经发布的决定需要通过明确的撤销或替代事件纠正。

其他公司、普通 Agent 任务和用户私人对话不自动进入当前公司的共享上下文。项目删除、权限调整和成员移除后，同步限制检索与后续投递。

## 6. 产物协作

代码任务为并行编辑成员提供独立工作树或分支，由指定整合成员合并并验证。无法使用 Git 的文档和目录采用明确的编辑归属及写入前版本检查。

成员可以共享项目目标，不能不加协调地同时写同一份文件。报告引用具体版本；验证成员检查的是被提交的同一产物版本，后续修改会使原验收结果失效。

分支隔离不适用于所有外部工具：共用数据库、浏览器账户或发布目标时，仍由项目资源权限与串行操作规则约束。成员交流不会自动授权对外发送消息或发布内容。

## 7. 界面草案

沿用简洁的聊天与任务界面，不引入虚拟办公室或场景动画。

- 顶部提供 **Agent / Company** 入口。
- Company 默认展示用户与负责人的总对话，以及需要关注的任务状态。
- 成员列表显示姓名、职责、当前工作、模型和运行状态。点开查看该成员的独立对话、工具执行和收件箱。
- 讨论区展示小组交流与直接消息，可按工作项查看。负责人汇报仍集中出现在总对话中。
- 任务区展示依赖、负责人、阻塞、验收和产物，允许用户调整分工。
- 每条消息保留发送时间、实际投递状态、所属工作项与来源引用；通知和提问不会跨公司或跨成员窗口弹错。
- 用户可以向负责人或指定成员发送消息。运行时默认排队，另提供手动引导；消息与附件沿用相同的交付规则。

Company 默认提供项目级全局观察者，成员观察者仍可分别开关。全局观察者查看当前目标、整个任务图、成员计划与已收到的消息、讨论和决策、产物版本、验收证据及资源消耗，判断团队是否持续朝目标推进。

观察采用事件触发、可调轮次与低频全局复核，按变化组织上下文。每次判断都会保存“不介入／证据不足／确认偏离／问题已解决”及依据。只有明确证据表明方向有误时才发纠偏提示；时间长、没有新聊天或观察者偏好不同，本身不能证明任务走错。

进程存活、超时收尾、消息投递与恢复由运行管理负责，不依赖模型观察者。关闭观察者只停止对应模型检查，不关闭这些基本运行保障。观察者拥有单独模型和思考强度配置，默认最高；记录随所属项目、成员对话和目标版本恢复。

## 8. 一个实际流程

用户要求：“检查论文的相关工作，核对基线归类，修改中英文说明并给出对照。”

1. 负责人明确修改范围和交付物，将文献核对与文稿修订分给成员。
2. 文献成员读取来源，发现 DLinear 不属于 Transformer、PatchTST 与 iTransformer 的 token 定义也不能混为一谈，直接向写作成员发送来源和影响。
3. 写作成员在现有上下文中接收该发现，修改两种语言的对应段落，并请文献成员核对术语。
4. 验证成员检查引用、范围限定、中英文一致性和修订后的文件版本，给出通过或具体问题。
5. 如果写作成员已经结束，验证提出的问题会自动唤醒它继续修订；完成通知再唤醒负责人汇总。
6. 用户在总对话看到最终修改、理由、来源和剩余问题，也可以展开查看任何一段讨论。

## 9. 与现有代码的关系

已有基础可复用：

- `lib/subagent/plan.js`、`admission.js`、`workflow-state.js`：工作拆分、依赖检查与展示。
- `lib/subagent-completion-queue.js` 和 `lib/subagent/completion-*`：完成通知、持久队列与唤醒方面的实现经验。
- `lib/z-core/*`：成员会话的运行状态、持久事件与恢复基础。
- `lib/task-memory-*` 与上下文检查点：限定范围的记忆、来源索引及成员上下文恢复。
- 现有模型选择、排队、引导、附件、观察者和工具执行界面。

现有实现还有几个需要明确补齐的边界：子代理工具明确禁止继续分派和跨会话操作，且限制为一层；完成通知的最终提交仍经过 renderer；Core 启动恢复只记录中断状态，不会自行恢复模型执行。这些都不能直接当作 Company 已具备的能力。

新增的 Company 层维护项目、成员、工作项、通信、决定、产物与预算。成员运行仍复用 Z 的执行能力，但不能仅解除现有临时子代理的限制来代替这层架构。部分现有子代理角色有只读或禁止继续分派的约束，需要为 Company 明确定义能力，不改坏 Agent 模式的默认行为。

建议模块划分（尚未实现）：

```text
lib/company/
  store.js       项目、成员、工作项、消息与回执
  scheduler.js   待办领取、并发预算、重启恢复与停止
  messaging.js   直接消息、讨论、汇报与投递
  workspace.js   产物版本、编辑归属与整合
  context.js     成员独立上下文与共享知识检索
  member-runtime.js 绑定成员身份、配置与 Z Core 执行
  service.js     独立常驻服务入口与控制接口
  supervisor.js  执行器和长任务存活核验、超时收尾
  recovery.js    启动核对、待办恢复与不确定结果处理
  observer.js    全局观察、证据检索与纠偏记录
lib/z-company-mcp.js 成员通信与工作项工具
renderer/
  company.js     总对话、成员、讨论、任务与产物视图
```

建议提供的成员工具包括：读取团队与工作项、发消息、创建讨论、汇报阻塞、提交产物、请求验证和记录决定。发送者身份、项目范围与权限由运行时确定，不能由工具参数任意冒充。

存储使用独立 Company 数据表与事务化收件箱/发件箱。共享大文件保存为产物引用；成员对话继续由会话系统保存，避免用一个巨大 JSON 文件混合所有成员历史。Core 的界面事件记录存在数量与文本长度限制，不能作为完整通信档案；Company 消息、决定和产物引用单独完整保存，广播为每个接收者分别记录回执。

## 10. 第一版验收范围

第一版必须完成真实的成员协作闭环：独立执行服务、创建团队、独立模型配置、直接消息、小组讨论、双路径唤醒、产物提交、独立验证、负责人汇报、全局观察者、用户暂停和重启恢复。先支持本机常驻服务与单项目团队，并完成持续运行验收；长期跨项目组织、多执行主机和自动招聘成员放到后续阶段。

必要的验证场景：

首先跑通一条完整链路：A 分派 B，B 直接询问 C，C 的回复唤醒 B，B 的成果再唤醒 A，最终把经验证的结果交给用户。

1. A 给正在工作的 B 发消息，消息出现在发送时的正确位置，且只被接入一次。
2. B 已结束后收到验证问题，无需切换窗口或手动说“继续”即可接续；用户主动停止时不唤醒。
3. 投递中重启、重复通知或模型请求失败，消息不丢失、不伪报已处理，也不重复执行不确定的外部操作。
4. 修改 A 的模型与思考强度不影响 B，活动轮次配置保持冻结。
5. 回退成员会话或修改任务版本后，旧待办不能污染新工作；已发布消息保持审计记录。
6. 两位成员修改同一产物时检测冲突；旧版本的验收结果不能自动证明新版本通过。
7. 无新证据的循环讨论会停止，依赖死锁能被明确指出，预算耗尽时保留结果并给出状态。
8. 公司间与普通对话间的消息、提问、记忆和工具权限保持隔离。
9. 界面完全退出后，成员仍能继续协作；服务重启后先核对执行现场，避免重复写入或假报完成。
10. 完成 72 小时持续运行及故障恢复验收，结果包含进展、资源趋势、成本与所有未决异常。目前这是验收目标，尚未执行。

完成这些之后，再增加团队模板、跨项目成员复用和长期组织记忆。
